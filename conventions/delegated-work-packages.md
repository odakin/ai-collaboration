# 相手側の AI への作業委譲 — 作業書 (work package) の形式

> 位置づけ: **自分**が別 session を起票して結果を回収するのは [`multi-session-coordination.md#spawn-handoff-token-return`](https://github.com/odakin/claude-config/blob/main/conventions/multi-session-coordination.md#spawn-handoff-token-return)、**相手側にも AI がいる並行作業**の一般則は [`dropbox-refs.md#counterpart-ai-parallel-work`](https://github.com/odakin/claude-config/blob/main/conventions/dropbox-refs.md#counterpart-ai-parallel-work)、**原稿改稿**を AI に実装させる記録形式は [`edit-intent-record.md`](edit-intent-record.md)。
> 本 doc はその隣 = **数か月の解析・調査を、相手 (人間 + その AI) に実行してもらう形に分割する**ときの文書形式。vendor 中立。

## <a id="why"></a>1. 何を分離するのか

相手側の AI に渡るのは **repo に置いた text だけ**である。こちらの hook も個人規約も session の文脈も届かない。したがって渡す前に、次の 2 つを分けて書き切る必要がある。

| | 誰のものか | どこに書くか |
|---|---|---|
| **判断** — 定義・手法・閾値・対象の選定・解釈・採否 | 依頼側 (と共著者の会議) | SPEC と WP の「やらないこと」、決定待ちの一覧 |
| **実行** — 実装・計測・検証・報告 | 相手側 (人間 + その AI) | WP の手順と受入基準 |

分けずに渡すと、相手の AI は**判断を埋めながら実行する**。埋めた判断は diff にも報告にも現れないので、後から「なぜこの閾値なのか」が誰にも分からなくなる。

## <a id="four-documents"></a>2. 常設 3 層 + WP

| 文書 | 中身 | 更新する人 |
|---|---|---|
| 入口 (`README`) | WP 一覧と**状態**、依存図、依頼側の決定待ち一覧、現在地 | 依頼側 (状態列だけ作業者も) |
| 手順 (`PROTOCOL`) | セッションの始め方、やってよい/いけないこと、止まる条件、返送様式、git の作法、書き込み zone | 依頼側 |
| 定義 (`SPEC`) | 問い、データ、定義、手法、判定、ファイル・命名・コード規約、記号表 | 依頼側 (**正本**。WP と矛盾したら SPEC が優先) |
| `WP<nn>` | 1 セッション分の作業 (下 §3) | 依頼側 |

**なぜ 3 層に割るか**: 相手の AI が毎回 context に載せる量を「入口 + 手順 + 定義 + WP 1 本」に収めるため。定義を各 WP に複製すると必ず drift する。SPEC を 1 つ置いて WP は短く書く。

**1 セッション = 1 WP = 1 結果ノート**。2 セッションかけて終わらなければ部分結果で `partial` と書いて止める、と PROTOCOL に明記する (延々と続けさせない)。

## <a id="wp-seven-parts"></a>3. WP 1 本の 7 要素

1. **目的** — この WP が終わると何が言えるようになるか (1〜3 文)
2. **入力** — 読む file・データ・参照値を path で
3. **手順** — 番号つき。関数名・CLI・出力 path まで書く。曖昧な語 (「適切に」「必要なら」) を残さない
4. **成果物** — どこに何を置くか (版管理する物と、再生成できる物を分ける)
5. **受入基準** — **数値で確認できる形**の表 (下 §4)
6. **止まる条件** — 続行より報告が価値をもつ場面を具体的に
7. **やらないこと** — 隣接して見える作業のうち、別 WP や依頼側の判断に属するもの

5 と 7 が肝である。5 が無いと「できました」しか返らず、7 が無いと勝手に隣まで進んで結論に混ざる。

## <a id="acceptance-from-own-implementation"></a>4. 受入基準は依頼側の独立実装で埋める

受入基準の理想形は「相手が出す数字」と「依頼側が別実装で出した数字」の一致である。

- 依頼側は WP を書く前に、**その WP の中核部分を自分で一度実装して参照値を作る**。参照値の表と生成 script を repo に commit し、WP の入力に「読んでよいが写さない。自分の実装を書き、結果で照合する」と書く
- 一致すれば**双方の実装が同時に検証される** (片方だけ正しくて一致することは、ほぼ無い)
- 一致しなければ、定義の解釈差か bug が**その場で**見える。どちらが正しいかは後で決めればよく、重要なのは食い違いが黙って通らないこと
- 参照値は絶対ではない。WP には「**参照値の方が誤っている可能性も排除しない**」と書く

⚠️ これは依頼側が中核を一度自分で書けるときにだけ使える。書けないなら、代わりに**合成データで真値を回収する test** を受入基準にする (真値を作るのは実装より安い)。

## <a id="write-all-start-ready"></a>5. 全部先に書き、着手は ready だけ

- 全 WP を最初に書き切る → 相手が**全体像と自分の位置**を見られる。「次は何か」を毎回聞かなくてよい
- ただし状態を 🟢 ready / 🟡 blocked / 🔵 進行中 / 🟣 done (review 待ち) / ✅ accepted / 🔁 rework で管理し、**依存が解けていない WP には着手させない**
- 後半の WP は前半の結果で細部が変わる。変わる部分は本文に埋め込まず「**確定待ち項目**」の箇条書きにして、依頼側が後で埋める
- 依頼側の判断が要る点は WP に散らさず、入口の**決定待ち一覧**に集約する (会議 1 回でまとめて決まる)

## <a id="write-zones"></a>6. 書き込み zone を分ける

衝突は規律でなく構造で避ける。

- **作業者**: コード・test・結果ノート・生成物・(入口の自分の行の状態列)
- **依頼側**: SPEC・WP・入口 (状態列以外)・repo の運用文書
- 相手が 🔵 進行中の WP について、依頼側はその出力先と該当モジュールを**読むだけ**にする
- 受け渡しは結果ノートの commit。依頼側が読んで ✅ accepted にするか、差し戻しを別 file に書く

## <a id="results-note"></a>7. 結果ノートの様式 (返送物)

template を repo に置き、コピーして書かせる。必須項目:

`status (done / partial / blocked)` / `環境 (OS・言語・主要ライブラリの版・commit)` / `やったこと` / `成果物の path 一覧` / **`受入基準の判定表 (1 行ずつ ✅❌⚠️ と根拠 file)`** / **`検証した範囲 / していない範囲`** / **`仕様への提案・気づき`** / `依頼側に決めてほしいこと` / `所要時間`

- 数値は結果ノートに再掲してよいが、**出典 file の path を必ず添える**。「記憶・過去ノート・推定から数値を書かない」と PROTOCOL に書く
- 「**仕様への提案**」欄が、SPEC を直す唯一の入口である。作業者に SPEC を直接編集させると正本が二重化する
- 「検証していない範囲」を必須にすると、`✅` の意味が「全部大丈夫」から「この範囲で確認」に変わる

## <a id="what-the-worker-must-not-write"></a>8. 作業者に書かせないもの

- **解釈・結論** — 「12 月は τ が大きい」(観察) は書かせる。「季節風のため」(解釈) は書かせない。解釈は著者が会議で決める
- **基準値の書き換え** — 受入基準に届かないとき、直すのは実装であって基準ではない。「参照値に合うまで手法をいじる」のは較正でなく捏造だと明記する
- **仕様外の解析の混入** — 思いついた追加解析は「提案」欄へ。結論に混ぜない

## <a id="when-not-to-use"></a>9. 使わない場面

- 相手が AI を使っておらず、作業書の粒度が細かすぎて失礼になるとき (人には目的と制約を渡し、手順は任せる)
- まだ探索段階で、定義も手法も書けないとき (**先に自分で pilot を回す**。SPEC が書けない状態で WP を書くと、判断を作業者に押し付けることになる)
- 1 回きりの小作業 (口頭とメールで足りる)

## <a id="origin"></a>10. 起源

- 2026-09-12、卒業論文を共著の国際誌論文に育てる解析プロジェクト (50 年の観測データ、実行者 = 学生本人 + その AI) を 15 本の WP に分割した際に形式化。同 repo の第 1 世代 = 入口 + 手順 + 定義 + WP00–14 で約 1,200 行
- 先行する経験: 相手側にも AI がいる並行作業で、交換 channel を「git に commit した note」に寄せると相手の AI が直接消費できると分かっていた ([`dropbox-refs.md#counterpart-ai-parallel-work`](https://github.com/odakin/claude-config/blob/main/conventions/dropbox-refs.md#counterpart-ai-parallel-work)、2026-08-29)。本 doc はその channel に**形式**を与えたもの
- ⚠️ **evidence base は 1 プロジェクト**。受入基準の本数・結果ノートの項目数は多すぎる可能性がある (形式が重いと中身が薄くなる)。2〜3 本の WP が accepted になった時点で「基準の数を減らす」方向に見直す
